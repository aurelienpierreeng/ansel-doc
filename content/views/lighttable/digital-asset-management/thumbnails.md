Each image in the current collection is represented by a thumbnail in the lighttable view and filmstrip module. A cache of the most recently used thumbnails is stored in a file on disk and loaded into memory at startup. The size of this cache can be adjusted in [Preferences > Processing > CPU, GPU, Memory](../../../preferences-settings/processing.md#cpu-gpu-memory).

## Thumbnail creation

A thumbnail is created when an image is imported into Ansel for the first time, after an image has been modified in the darkroom, or when revisiting an image whose thumbnail is no longer available.

When an image is imported for the first time Ansel can either try to extract an embedded thumbnail from the input image (most raw files contain these, usually in JPEG format) or process the raw image itself using default settings. Choose how Ansel obtains its thumbnails from the global menu **Display** 🡒 **Thumbnail source** — **Always process the RAW**, **Use embedded JPG if unedited**, or **Always use embedded JPG**. This can be changed at runtime.

Extracting an embedded thumbnail from the input image is usually very fast. However, these thumbnails have been generated by the raw converter of the camera and do not represent Ansel's “view” of that image. You will notice the difference as soon as you open the image in the darkroom mode, at which point Ansel replaces the thumbnail with its own internally processed version.

After import Ansel automatically generates thumbnails for new images as they are needed. When importing a large set of new images, thumbnail generation can slow down navigation in the lighttable view. Alternatively you may terminate Ansel and generate the thumbnail cache separately by running [`ansel-generate-cache`](../../../cli/ansel-generate-cache.md). This program will generate all missing thumbnails in one go.

As the thumbnail cache has a pre-defined maximum size it will eventually get filled up. If new thumbnails are subsequently added, old thumbnails are dropped from the cache. However, Ansel will keep all thumbnails on disk if the corresponding disk backend option is activated in [Preferences > Processing > CPU, GPU, Memory](../../../preferences-settings/processing.md#cpu-gpu-memory). Access to the thumbnails in this secondary cache is slower than the primary cache, but still much faster than reprocessing thumbnails from scratch. The size of the secondary cache is limited only by the available disk space.

You can pre-render or purge cached thumbnails for the selected images at runtime from the global menu **Run** 🡒 **Preload selected thumbnails in cache** and **Purge selected thumbnails from cache**.

Thumbnails are never removed automatically from the secondary cache. You can manually clean it by recursively deleting all images in the `$HOME/.cache/ansel/mipmaps-xyz.d` folder (where `xyz` denotes an alphanumeric identifier of the cache). After clearing the secondary cache you can simply let Ansel re-generate thumbnails as needed, or generate them all in one go with [`ansel-generate-cache`](../../../cli/ansel-generate-cache.md).

If you choose not to activate the disk backend and select too small a cache size, Ansel may become unresponsive, you may experience continuous regeneration of thumbnails when you navigate your collection or flickering of thumbnail images. A good choice of cache size is 512MB or higher (see [Memory and performance tuning](../../../preferences-settings/performance/mem-performance.md) for more information).

All thumbnails are fully color managed. Colors are rendered accurately on screen as long as your system is properly set up to hand over the right monitor profile to Ansel. For more information see the [color management](../../../color-management/_index.md) section.

## Skulls

When Ansel cannot produce a thumbnail, it shows a skull in its place, with a short message naming the reason. A skull only concerns the thumbnail: the image file, its editing history and its sidecar are left untouched, and the thumbnail comes back once the cause is fixed.

{{< figure src="skull.jpg" alt="skull thumbnail" class="align-left borderless tight" />}}

{{< note >}}
- On a small thumbnail, the message may be cut short with an ellipsis: lower the number of [columns](../_index.md#columns-grid-size) of the lighttable grid to make the thumbnails larger and read it in full.
- A skull stays there even after its cause has gone away. Once you have fixed the cause, select the affected images and choose **Run** 🡒 **Purge selected thumbnails from cache** to have their thumbnails generated again. A purge does not reload a file that Ansel had already decoded successfully: if you replaced such a file and the skull comes back, restart Ansel.
{{< /note >}}


Each message names one cause, listed here with what to do about it. When the skull comes from a file Ansel could not decode — _I/O error_, _Corrupted file_, _Unsupported camera_, _Unsupported feature_ or _Loading error_ — a notification also says _The file … is supported by none of our decoders_.

{{< param-table >}}
| **File not found**<div>
Ansel found the image file neither at the location recorded in its library nor as a [local copy](local-copies.md). Ansel does not follow files that are changed outside of it: the file was moved, renamed or deleted, or it is stored on a drive that is not connected at the moment — an external disk, a memory card or a network share.

- If the drive is disconnected, connect it again so that the file is back at the same path, then purge the thumbnail.
- If you moved or renamed the folder, give Ansel its new location with **relocate…** in the _Folders_ tab of the [Library module](../../toolboxes/collections.md#updating-the-folder-path-of-moved-images), then purge the thumbnail.
- If you deleted the file on purpose, remove the image from the library as well, with **File** 🡒 **Remove from library**. To find and remove every image whose file is gone, close Ansel and run [`purge_non_existing_images.sh`](../../../cli/purge_non_existing_images_sh.md).
</div> |
| **I/O error**<div>
The file is where Ansel expects it, but Ansel could not read it: the file is empty, or your user account is not allowed to read it. Ansel refuses such a file at import, so it has changed since — emptied by an interrupted copy or synchronization, for instance, or given other permissions.

- If the file is empty, copy it again from the memory card or from a backup, then purge the thumbnail.
- If the file cannot be read, give your user account the permission to read it, then purge the thumbnail.
</div> |
| **Corrupted file**<div>
The file is there, but none of Ansel's decoders could read it: either it is damaged — typically cut short by an interrupted copy from the memory card, or by a failing disk — or it holds data in a format Ansel does not know, whatever its extension.

1. Try to open the file in another application. If it fails there too, the file is damaged: copy it again from the memory card or from a backup, then purge the thumbnail.
2. If the file opens elsewhere, Ansel does not support its format: report it on the [Ansel issue tracker](https://github.com/aurelienpierreeng/ansel/issues).
</div> |
| **Unsupported camera**<div>
The file is a raw file from a camera model that none of Ansel's raw decoders supports.

Report the camera model on the [Ansel issue tracker](https://github.com/aurelienpierreeng/ansel/issues), attaching a raw file from that camera if you can.
</div> |
| **Unsupported feature**<div>The file is a raw file that uses a feature of its format that Ansel's raw decoders do not handle. Report it on the [Ansel issue tracker](https://github.com/aurelienpierreeng/ansel/issues), attaching the file.</div> |
| **Loading error**<div>Ansel's raw decoder recognized the file but could not load its image data. Report it on the [Ansel issue tracker](https://github.com/aurelienpierreeng/ansel/issues), attaching the file.</div> |
| **Out of RAM**<div>
Ansel could not get the memory it needed to produce the thumbnail, either to load the image at full size — a _Not enough memory_ alert is then shown as well — or to process it. This depends on what else was using memory at that moment, inside or outside of Ansel, so the same image may render without trouble later.

Close other applications to free memory, then purge the thumbnail. If it happens often, review the memory settings in [Preferences > Processing > CPU, GPU, Memory](../../../preferences-settings/processing.md#cpu-gpu-memory), with the help of [memory and performance tuning](../../../preferences-settings/performance/mem-performance.md).
</div> |
| **No embedded thumbnail**<div>
**Display** 🡒 **Thumbnail source** is set to **Always use embedded JPG**, which forbids Ansel to process the image itself, and there is no JPEG it could use for this image: neither a companion JPEG — a file with the same name and a `.jpg` or `.jpeg` extension, in the same folder — nor a readable preview embedded in the file. Not every file carries an embedded preview.

Choose **Use embedded JPG if unedited** in **Display** 🡒 **Thumbnail source**: Ansel then processes any image that has no usable preview, instead of showing a skull. Changing the thumbnail source regenerates the thumbnails of the whole collection, so no purge is needed.
</div> |
| **Processing error**<div>
The file was read, but processing it produced no thumbnail: the processing pipeline could not be set up, or one of the modules in the image's history failed. A module that runs out of memory also ends up here, rather than under _Out of RAM_.

1. Purge the thumbnail to try again, in case the failure was momentary.
2. If the skull comes back, open the image in the [darkroom](../../darkroom/_index.md) to check whether it renders there.
3. Report the problem on the [Ansel issue tracker](https://github.com/aurelienpierreeng/ansel/issues), attaching the image file and its [XMP sidecar](sidecar.md), which holds the history needed to reproduce the failure.
</div> |
| **Aborted**<div>The processing of the thumbnail was stopped before it finished. Nothing is wrong with the image: purge the thumbnail to have it generated again.</div> |
{{< /param-table >}}
